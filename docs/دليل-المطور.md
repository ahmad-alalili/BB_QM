# دليل المطور — منشئ أسئلة Blackboard

هذا الدليل للمبرمج الذي يستلم المشروع، وليس للمستخدم النهائي. دليل الاستخدام
المصوّر 2.5 الموجود في هذا المجلد يشرح تشغيل الموقع للمدرب.

## 1. حالة هذه النسخة

- مستودع الموقع المنشور على GitHub Pages؛ الدفع إلى `main` يحدّث الموقع العام.
- المرجع هو الإصدار المنشور 2.5، والالتزام `f89c069c72d147366e8376305085c6bfa0b7cd17`.
- إعادة التنظيم لا تغيّر شكل الصفحة أو أنواع الأسئلة أو النقاط أو حد 250 سؤالًا.
- اختبر التعديلات محليًا قبل النشر، ولا تعدّل خدمة Cloudflare أو بياناتها ضمن صيانة الواجهة.
- احتُفظ بالواجهة العامة للنواة `BlackboardCore` وبأسماء دوالها؛ لذلك تبقى
  اختبارات التصدير والجهات المستدعية متوافقة مع النسخة السابقة.

## 2. أول تشغيل

تحتاج Node.js 18 أو أحدث لتشغيل الأوامر. لا توجد حزم تحتاج إلى تنزيلها لهذا المشروع.
افتح الطرفية داخل مجلد هذه النسخة، ثم نفّذ:

```powershell
npm start
```

افتح الرابط الذي تعرضه الطرفية. المنفذ الافتراضي هو 61053. لتحديد منفذ مختلف:

```powershell
npm start -- 8767
```

أوقف الخادم بـ Ctrl+C. يستمع الخادم على `127.0.0.1` فقط، ولا يفتح الموقع للشبكة.
يمكن أيضًا فتح `index.html` مباشرة دون خادم؛ لكن تشغيله محليًا أفضل لاختبار الحافظة.

للتحقق من الملفات ثم تشغيل الاختبارات:

```powershell
npm run check
npm test
```

لا توجد خطوة بناء أو ملفات JavaScript مولّدة. الملف الذي تعدّله هو الذي يحمّله
المتصفح. حدّث الصفحة بعد حفظ التعديل. خادم المعاينة يعطّل التخزين المؤقت محليًا.

## 4. أين أعدّل الميزة؟

تحديث المظهر المحلي في 2026-09-12: اسم Cairo الظاهر في القائمة هو
«خط المؤسسة للتدريب التقني والمهني» بناءً على طلب صاحب المشروع؛ هذه تسمية
للواجهة وليست تغييرًا لاسم الخط الأصلي أو ترخيصه أو ادعاء اعتماد رسمي.
يبقى Cairo الافتراضي مع احترام اختيار المستخدم المحفوظ. يأتي `cursor.css`
بعد `theme.css`؛ لا يوجد تتبع لحركة الماوس أو إرسال بيانات بسبب المؤشر.

### مثال: تغيير لون الأنواع المحددة

ابدأ من `theme.css` وابحث عن `--glass-emerald` و`--jewel-green` وقواعد النوع المحدد.
لا تضف قاعدة مماثلة إلى ملف آخر قبل فحص القاعدة الحالية. الملف يُحمّل بعد ملفات
التنسيق الأخرى؛ لذا قد يتغلب على اللون الأساسي في `styles.css`.

### مثال: تعديل رسالة ترشيح الذكاء الاصطناعي

النص داخل `index.html` عند `model-advice-dialog`. توقيت الظهور وحفظ خيار عدم التذكير
في `src/ui/prompt-editor.js`. اختبر نجاح التوليد وفشله وإعادة فتح الصفحة، لا النص وحده.

### مثال: إضافة نوع سؤال

ليست مجرد إضافة خيار HTML: راجع إعدادات النوع، وعقد JSONL، والتحقق، والبرومبت،
والمعاينة، وكل مسار تصدير يدعمه، واختباراته. توافق الإحصائيات والخدمة الخلفية
يحتاج مراجعة مستقلة؛ لا تعدّل خدمة الإنتاج من هذه النسخة المحلية.

## 5. كيف تتصل الأجزاء؟

مسار البيانات:

```text
حقول index.html
  -> سياق الصفحة ووحدات src/ui
  -> دوال core.js العامة
  -> وحدات src/core المتخصصة
  -> نتيجة أو أخطاء
  -> المعاينة ومحرر النقاط
  -> مراجعة نهائية ثم تنزيل
```

وحدات النواة لا تستخدم `document` ولا تعدّل الواجهة. تستورد احتياجاتها بأسماء واضحة
وتعيد دوالها. في Node تُحمّل بـ `require`، وفي المتصفح تُسجّل ضمن `BBQuestionModules`.
هذه طريقة للحفاظ على التشغيل المباشر للملف دون نظام بناء؛ لا تستخدم `import` في
ملف واحد فقط دون تحديث طريقة التشغيل والاختبارات للمشروع كله.

كل وحدة واجهة تصدّر `create(context, actions)`:

- `context.elements`: مراجع الحقول، تُجمع في `src/ui/context.js` مرة واحدة.
- `context.state`: حالة الصفحة في الذاكرة، مثل البرومبت ومسودة النقاط. لا تنشئ نسخة
  ثانية من الحالة نفسها في وحدة أخرى، ولا تحفظ المحتوى في التخزين دون طلب واضح.
- `actions`: الدوال التي توفرها وحدات الواجهة لبعضها. يربطها `app.js` مرة واحدة؛
  لا تستدعِ دوال وحدة أخرى أثناء إنشاء الوحدات، بل بعد اكتمال الربط عند تفاعل المستخدم.
- الأحداث الرئيسية تُربط في `app.js`، وأحداث الحقول المنشأة ديناميكيًا تبقى في محررها.

تتحقق الاختبارات من عدم تكرار أسماء الدوال ومن وجود جميع الدوال المشار إليها.
عند إضافة وحدة، أضف تحميلها في `index.html` قبل `app.js` وسجّلها في قائمة الوحدات.

## 6. ترتيب التنسيق والتحميل

ترتيب CSS الحالي مقصود: الأساسي، ثم الاستجابة، ثم شاشة الإحصائيات، ثم الثيم، ثم المؤشر.
أبقينا هذا الترتيب أثناء إعادة التنظيم لحماية الشكل الذي تمت مراجعته. لا تنقل
القواعد بين الملفات عشوائيًا، ولا تكثر من `!important` لمعالجة تعارض لم تفهم سببه.

تُحمّل ملفات JavaScript باستخدام `defer`. وحدات النواة تسبق `core.js`، ووحدات الواجهة
تسبق `app.js`. إذا نقلت ملفًا، حدّث مساره في HTML وفي `require` وفي التوثيق، ثم افحص
التشغيل من الخادم ومن ملف HTML المباشر.

## 7. الاختبارات قبل اعتبار التعديل جاهزًا

1. شغّل فحص الملفات والاختبارات.
2. جرّب تعديلك كاملًا في المتصفح، وليس حالة النجاح الوحيدة.
3. اختبر الهاتف والكمبيوتر، والتخطي في شاشة الدخول، واختيار الخط.
4. إذا تغيّرت الأعداد: اختبر إلغاء نوع ثم إعادته والتبديل بين الوضعين.
5. إذا تغيّر البرومبت: اختبر التوليد والتعديل والمسح والاستعادة وظهور رسالة الترشيح.
6. إذا تغيّرت النقاط أو التصدير: راجع المعاينة، ثم افحص البنك والاختبار المباشر وTXT
   كلًا على حدة. لا تفترض أن توافق إحداها يثبت توافق الأخرى.
7. راجع `BLACKBOARD-ACCEPTANCE.md` لاختبار الاستيراد والتصحيح داخل مقرر تجريبي.

المخرجات المرجعية في الاختبارات مأخوذة من الإصدار قبل إعادة التنظيم. لا تحدّثها
تلقائيًا لمجرد فشل اختبار؛ افهم فرق المخرجات أولًا. بعض الاختبارات القديمة تفحص
بنية النص أو CSS، وليست دليلًا على سلامة العرض في متصفح حقيقي.

## 8. حدود مهمة لا تغيّرها عرضًا

- الإصدار الظاهر للمستخدم 2.5؛ رقم المحرك الداخلي 2.16.2، وله غرض مستقل.
- الحد الحالي 250 سؤالًا للدفعة؛ توجد ضوابط مرتبطة به في عدادات الخدمة الخلفية.
- لا تُرسل نصوص المادة أو البرومبت أو الرد أو قيم الدرجات إلى الإحصائيات.
- ملفات Native للبنك والاختبار المباشر منفصلة؛ مولّد QTI القديم للمقارنة الداخلية فقط.
- TXT لا يحمل النقاط المخصصة. المعادلات المحسوبة الحالية ثابتة وليست توليدًا عشوائيًا.
- لا تستخدم `eval` لتفسير المعادلات، ولا `innerHTML` لعرض رد الذكاء الاصطناعي.

## 9. حدود تحديث النشر

لم نغيّر نصوص كتيب المستخدم أو صيغ التصدير. التغييرات البصرية تخص اسم الخط والمؤشر ومساحة قائمة الخط.
لم ننقل خدمة Cloudflare إلى هذا المجلد، ولم نعدّل بياناتها.
عزلنا الصفحة التاريخية بصيغة نصية في الأرشيف، بدل حذفها أو اعتبارها نقطة تشغيل ثانية.
قبل أي نشر لاحق، راجع الفروق والاختبارات أولًا ثم استخدم مسار النشر المعتمد؛
وجود نسخة محلية ناجحة لا يُعد إذنًا بتحديث الموقع العام.
